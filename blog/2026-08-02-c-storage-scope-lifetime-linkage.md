# 存储类、作用域、生命周期、链接属性：C 变量的"四维身份"

## 引言：同一个变量，四个不同的问题

面对 C 语言中的任何一个变量或函数，你可以问出四个看似简单、却最能考验功底的问题：

1. **它存在哪里？** —— 栈上、堆上、数据段、还是代码段？
2. **哪些代码看得见它？** —— 只在当前函数里，还是整个文件，甚至整个程序？
3. **它什么时候诞生、什么时候消亡？** —— 函数调用期间，还是程序运行全程？
4. **别的 .c 文件能访问它吗？** —— 会不会和别的文件里的同名符号冲突？

这四个问题，分别对应 C 语言中的 **存储类（Storage Class）**、**作用域（Scope）**、**生命周期（Lifetime）** 和 **链接属性（Linkage）**。

很多同学能把 `static`、`extern`、`volatile` 的关键字背得滚瓜烂熟，但一旦遇到"为什么函数不能返回局部变量的地址""为什么全局变量定义不能放 .h 文件""为什么裸机下全局变量初值会不对"这类问题就卡壳——根本原因就是这 4 个概念没有串成体系。本文基于 C89/C99/C11 标准，把这 4 个概念一网打尽，并结合嵌入式工程实践讲透。

---

## 一、四个核心概念总览

| 概念 | 回答的问题 | 决定因素 |
|------|-----------|---------|
| 存储类（Storage Class） | 变量存在哪里？（栈/堆/数据段/BSS段/代码段） | 定义方式（关键字、位置） |
| 作用域（Scope） | 变量在哪些代码范围内可见？ | 定义位置（代码块内/文件内） |
| 生命周期（Lifetime） | 变量什么时候诞生、什么时候消亡？ | 存储位置（栈/堆/数据段） |
| 链接属性（Linkage） | 变量/函数跨文件能否被访问？ | 关键字（static/extern） |

这 4 个概念从 4 个不同角度描述一个变量/函数的完整行为特征。**先有存储位置，才决定生命周期；由定义位置，推出作用域；由关键字，决定链接属性**——它们之间既有联系又相互独立。

## 二、Linux 下 C 程序的内存映像

这是理解存储类和生命周期的基础。一个 Linux 进程的虚拟地址空间从上到下大致如下：

```
高地址 0xFFFFFFFF
+---------------------------+
|     内核映射区            |  ← 操作系统内核（3-4GB）
|     （Kernel Space）      |
+---------------------------+
|     栈（Stack）           |  ← 局部变量、函数调用帧
|     ↓ 向下增长           |
+---------------------------+
|     文件映射区            |  ← 动态库、mmap映射文件
|     （File Mapping）      |
+---------------------------+
|     ↑ 向上增长           |
|     堆（Heap）            |  ← malloc/free 手动管理
+---------------------------+
|     BSS段                |  ← 未初始化/初始化为0的全局变量
|     （.bss）             |     static局部变量
+---------------------------+
|     数据段（.data）       |  ← 显式初始化为非0的全局变量
|                         |     static局部变量
+---------------------------+
|     只读数据段（.rodata） |  ← const常量、字符串常量
+---------------------------+
|     代码段（.text）       |  ← 函数代码（指令）
+---------------------------+
低地址 0x00000000
```

### 各段详细说明

| 段 | 存放内容 | 特点 |
|----|---------|------|
| 代码段（.text） | 函数编译后的机器指令 | 只读，程序终止时消亡 |
| 只读数据段（.rodata） | const常量、字符串常量 | 只读，程序终止时消亡 |
| 数据段（.data） | 显式初始化为非0的全局变量、static局部变量 | 可读写，程序启动时初始化 |
| BSS段（.bss） | 未初始化/初始化为0的全局变量、static局部变量 | 可读写，程序启动时清零 |
| 堆 | malloc()/calloc()分配的内存 | 手动申请、手动释放 |
| 栈 | 局部变量、函数参数、返回地址 | 自动分配、自动释放 |
| 文件映射区 | 动态库、mmap()映射的文件 | 按需加载 |

### OS 下 vs 裸机下的差异

- **OS 下**：启动代码（crt 运行时库）自动完成 .data 初始化、.bss 清零、栈设置，程序员无需关心；
- **裸机下**：需要在启动汇编代码（startup 文件）中**手动**做 .data 重定位和 .bss 清零，否则全局变量初值不对。这一点在第九节的嵌入式实战中会展开。

## 三、存储类关键字详解

C 标准规定的存储类说明符（storage-class specifier）共有 5 个：`auto`、`register`、`static`、`extern`、`_Thread_local`（C11 引入，C23 起改名 `thread_local`），外加语法上占位的 `typedef`，以及修饰性质的 `volatile`、`restrict`。

### 3.1 auto —— 自动局部变量

```c
auto int a = 10;   // 等价于 int a = 10;
```

特征：

- 修饰局部变量，分配在栈上；
- **默认省略**（不写就是 auto）；
- 不初始化则值为**随机值**；
- 作用域：代码块内；生命周期：函数调用期间。

### 3.2 register —— 寄存器变量

```c
register int counter = 0;
```

特征：

- 建议编译器将变量放在 CPU 寄存器中（读写速度最快）；
- 编译器**不一定采纳**（寄存器数量有限）；
- **不能取地址**（`&counter` 会报错），不能使用对齐说明符（`_Alignas`），register 数组不能转换为指针；
- 可以用于函数参数列表；
- 典型应用：uboot 中的 `gd`（global data）变量，被高频访问。

适用场景：循环变量、高频访问的全局数据。但现代编译器优化已经很好，**不要随意使用**。

### 3.3 static —— 两种完全不同的用法

这是 C 语言中最复杂、最重要的关键字之一。

**用法一：修饰局部变量 → 静态局部变量**

```c
void func() {
    static int count = 0;  // 只初始化一次
    count++;
    printf("%d\n", count);
}
// 多次调用func()，输出1,2,3,4... 每次累加
```

| 对比项 | 普通局部变量 | 静态局部变量 |
|--------|------------|------------|
| 存储位置 | 栈 | 数据段/bss段 |
| 初始化值 | 不初始化=随机 | 不初始化=0 |
| 生命周期 | 函数调用期间 | 整个程序运行期间 |
| 作用域 | 代码块内 | 代码块内 |
| 初始化时机 | 每次调用时 | 程序启动时（仅一次） |

注意：static 局部变量的作用域仍然是**代码块内**，只是生命周期被拉长了——这是"存储位置决定生命周期"的典型例子。

**用法二：修饰全局变量/函数 → 静态全局变量/静态函数**

```c
// file1.c
static int g_counter = 0;   // 只能在file1.c中访问
static void helper() {}     // 只能在file1.c中调用

// file2.c 中无法访问 g_counter 和 helper()
```

作用：将链接属性从**外链接**改为**内链接**，限制符号只在当前 .c 文件内可见。

工程意义：**防止多文件编译时的符号重名冲突**（详见 6.5 节）。

### 3.4 extern —— 跨文件声明

```c
// a.c
int g_global = 100;

// b.c
extern int g_global;   // 告诉编译器：这个变量在别的文件里定义
void func() {
    int x = g_global;  // 可以使用
}
```

要点：

- `extern` 是**声明（不是定义）**，不分配内存；
- 告诉编译器符号在其他文件中定义，链接时会去别处找；
- 编译以单个 .c 文件为单位，没有声明会报错；
- 若 `extern` 重声明一个先前已声明为**内链接**的标识符，其链接属性**保持内链接**不变（C 标准规定）。

### 3.5 volatile —— 易变的

```c
volatile int flag = 0;
```

含义：告诉编译器，这个变量可能被**编译器之外的力量**改变，不要做优化。

**三种必须使用 volatile 的场景：**

| 场景 | 示例 |
|------|------|
| 中断服务程序（ISR）中修改的变量 | 硬件中断触发，异步修改 |
| 多线程共享的变量 | 其他线程修改，编译器不知道 |
| 硬件寄存器地址映射 | 硬件自动改变寄存器值 |

编译器优化的危害（不加 volatile 的后果）：

```c
int flag = 0;
while (flag == 0) {   // 如果flag在ISR中改变
    // 编译器可能优化为：if (flag == 0) while(1);
    // 导致永远跳不出循环
}
```

### 3.6 restrict —— 唯一访问指针（C99）

```c
void copy(int *restrict dst, int *restrict src, int n) {
    while (n--) *dst++ = *src++;
}
```

含义：告诉编译器，该指针指向的内存区域**只能通过这个指针访问**，不会有其他指针别名指向同一块内存。

作用：允许编译器做更激进的优化（如流水线、向量化）。

注意：`memcpy` 和 `memmove` 的区别——`memcpy` 用 restrict（不允许重叠），`memmove` 不用（允许重叠，更安全但略慢）。

### 3.7 typedef —— 类型重命名

```c
typedef unsigned int uint32_t;
typedef int (*FuncPtr)(int, int);  // 函数指针类型
```

虽然 C 标准把 `typedef` 归类为存储类关键字，但它实际和存储类无关，只是语法上占了一个关键字位置。

### 3.8 C11 补充：_Thread_local —— 线程存储期

这里补上 C11 引入的线程存储期说明符：

```c
// C11：_Thread_local；C23 起改名 thread_local
_Thread_local int tls_counter = 0;

// 块作用域使用时，必须配合 static 或 extern 决定链接属性
void func(void) {
    static _Thread_local int local_tls = 0;
}
```

要点：

- 每个线程拥有**独立的一份**对象副本，存储期与线程生命周期相同；
- 不能用于函数声明；如果一个对象用了它，其**每一次声明**都必须带上它；
- 通常通过 `<threads.h>` 中定义的宏 `thread_local` 来写（`#include <threads.h>` 后可直接写 `thread_local int x;`）；
- 在嵌入式 RTOS 中，等价物是各任务私有的静态数据（或 TCB 中的私有字段），裸 C 的 `_Thread_local` 依赖编译器支持（如 GCC 的 `__thread`）。

### 3.9 默认存储类说明符

不写任何存储类关键字时，编译器按默认规则处理：

- **函数** → 默认 `extern`（外链接）；
- **文件作用域对象**（全局变量）→ 默认 `extern`；
- **代码块作用域对象**（局部变量）→ 默认 `auto`。

还有一个易踩坑的细节（cppreference 明确记载）：**C 语言中，文件作用域的 `const` 变量默认是外链接；而 C++ 中文件作用域的 const 默认是内链接**。跨语言移植时（如把 C 代码编成 C++）要注意，否则可能出现"多个定义"链接错误。

## 四、作用域详解

### 4.1 作用域类型总览

| 作用域类型 | 适用对象 | 范围 |
|-----------|---------|------|
| 代码块作用域 | 局部变量 | 从定义处到所在 {} 结束 |
| 文件作用域 | 全局变量、函数 | 从定义处到文件末尾 |
| 函数作用域 | goto标签 | 整个函数内 |
| 函数原型作用域 | 函数声明中的参数 | 声明括号内 |

### 4.2 代码块作用域示例

```c
void func() {
    int a = 10;          // a的作用域从这里开始
    if (a > 5) {
        int b = 20;      // b的作用域：if的{}内
        a = b;           // ✅ 可以访问a
    }
    // b在这里不可见 ❌
}
```

### 4.3 文件作用域（全局）

```c
#include <stdio.h>
int g_value = 100;      // 文件作用域：从这行到文件末尾

void func1() {
    g_value = 200;      // ✅ 可访问
}

void func2() {
    g_value = 300;      // ✅ 可访问
}
```

### 4.4 同名变量掩蔽规则

```c
int a = 100;            // 全局变量（文件作用域）

void func() {
    int a = 50;         // 局部变量（代码块作用域），掩蔽全局a
    printf("%d\n", a);  // 输出50（局部变量）

    if (1) {
        int a = 30;     // 更内层，掩蔽外层局部a
        printf("%d\n", a); // 输出30
    }
    printf("%d\n", a);  // 输出50（外层局部a）
}
```

原则：**作用域小的掩蔽作用域大的**（"县官不如现管"）。

### 4.5 C89 vs C99 变量定义位置差异

**C89（ANSI C）**：变量必须在代码块**最前面**定义：

```c
void func() {
    int a;     // ✅
    a = 10;
    int b;     // ❌ C89报错，C99允许
    b = 20;
}
```

**C99（及之后）**：变量可以在代码块任意位置定义，遵循"先定义后使用"即可。

> 嵌入式提醒：Keil MDK / IAR 的默认 C 标准是 C90（≈C89），很多老工程里变量必须声明在块开头；GCC（arm-none-eabi-gcc）默认 `-std=gnu11` 或 `gnu17`，则无此限制。跨工具链移植代码时要特别注意。

## 五、生命周期详解

### 5.1 生命周期类型对比

C 标准定义了 4 种存储期（storage duration）：

| 存储位置 | 生命周期类型 | 诞生时机 | 消亡时机 |
|---------|------------|---------|---------|
| 栈 | 自动存储期 | 进入代码块时 | 离开代码块时 |
| 堆 | 分配存储期 | malloc时 | free时 |
| 数据段/bss段 | 静态存储期 | 程序加载时 | 程序终止时 |
| 线程局部存储 | 线程存储期（C11） | 线程创建时 | 线程结束时 |

> C99 还有一个特例：**变长数组（VLA）** 的存储期是"声明执行时分配、超出作用域时释放"，而不是进入代码块时分配。

### 5.2 栈变量的生命周期（自动存储期）

```c
void func() {
    int a = 10;      // 调用func时，在栈上分配a
    // ... 使用a
}                    // func返回时，a消亡（栈空间被回收）
```

**思考：为什么函数不能返回局部变量的地址？**

```c
int* func() {
    int a = 10;
    return &a;       // ❌ 危险！a在func返回后已经消亡
}
```

返回后该指针成为**悬垂指针（dangling pointer）**，指向的内存随时可能被其他函数复用——这是 C 面试高频题，也是实际工程 bug 的重灾区。

### 5.3 堆变量的生命周期（分配存储期）

```c
void func() {
    int *p = (int*)malloc(sizeof(int));  // 堆上分配，p诞生
    *p = 10;
    // ...
    free(p);         // p消亡（内存被释放）
}
```

关键：malloc 后不 free → **内存泄漏**；free 后继续使用 → **野指针访问**（use-after-free）。

### 5.4 全局变量/静态变量的生命周期（静态存储期）

```c
int g_global = 100;        // 程序启动时分配，终止时释放
static int s_static = 50;  // 同上

int main() {
    // g_global和s_static在整个程序运行期间一直存在
    return 0;
}
```

### 5.5 用"图书馆借书"类比记忆

| 变量类型 | 类比 | 说明 |
|---------|------|------|
| 栈变量 | 去图书馆临时阅览室看书 | 进来看，出去就还了 |
| 堆变量 | 去借书处借书 | 借了用，用完要还（free） |
| 全局变量 | 自己买的书 | 一直拥有，直到"搬家"（程序终止） |

## 六、链接属性详解

### 6.1 编译与链接的过程

```
源文件1.c → 编译 → 目标文件1.o
源文件2.c → 编译 → 目标文件2.o
源文件3.c → 编译 → 目标文件3.o
                    ↓ 链接
               可执行程序
```

- **编译阶段**：以单个 .c 文件为单位，生成 .o 目标文件；
- **链接阶段**：将所有 .o 文件合在一起，解析符号引用。

### 6.2 三种链接属性

| 链接属性 | 作用范围 | 适用对象 | 关键字 |
|---------|---------|---------|--------|
| 外链接（External） | 整个程序（所有.c文件） | 普通函数、普通全局变量 | 默认（无） |
| 内链接（Internal） | 当前.c文件内 | 静态函数、静态全局变量 | static |
| 无链接（No Linkage） | 不参与链接 | 局部变量（auto/static/register） | 不参与 |

### 6.3 外链接示例

```c
// a.c
int g_value = 100;        // 外链接
void func1() { ... }      // 外链接

// b.c
extern int g_value;       // 声明a.c中定义的变量
void func1();             // 声明a.c中定义的函数

void func2() {
    g_value = 200;        // 可以使用
    func1();              // 可以调用
}
```

### 6.4 内链接示例

```c
// a.c
static int g_value = 100;   // 内链接，只在a.c中可见
static void func1() { ... } // 内链接，只在a.c中可见

// b.c
extern int g_value;         // ❌ 链接失败：g_value在b.c中不可见
void func1();               // ❌ 链接失败：func1在b.c中不可见
```

### 6.5 static 的第二种用法 —— 解决符号重名问题

C 语言没有 C++/Java 的命名空间（namespace），在多文件大型项目中，符号重名是严重问题。

解决方案：用 `static` 将不需要跨文件访问的符号设为内链接。

```c
// file1.c
static int counter = 0;     // 只在file1.c中使用，不暴露
static void helper() {}     // 只在file1.c中使用，不暴露

int public_func() {         // 外链接，暴露给其他文件
    helper();               // 可以调用static函数
    counter++;
}
```

```c
// file2.c
static int counter = 0;     // 和file1.c中的counter重名，但没问题（都是static）
static void helper() {}     // 和file1.c中的helper重名，但没问题
```

如果没有 static，两个 counter 就会冲突，链接报错 `multiple definition`。

### 6.6 全局变量的定义 vs 声明

| 写法 | 含义 |
|------|------|
| `int g_val;` | 可能是定义，也可能是声明（试探性定义，编译器看情况） |
| `int g_val = 0;` | 明确的定义（有初始化） |
| `extern int g_val;` | 明确的声明（告诉编译器在别处定义） |

> 关于 `int g_val;`：C 标准称之为**试探性定义（tentative definition）**——文件作用域、无初始化、无 extern 的声明。多个翻译单元中若出现多个试探性定义，链接器通常将其合并为一个；但如果与其他**明确的定义**冲突，行为是未定义的（undefined behavior）。

**工程规范：**

```c
// module.h
extern int g_module_var;   // 声明（告诉别人有这个变量）
void module_func();

// module.c
int g_module_var = 100;    // 定义（分配内存，初始化）
void module_func() { ... }
```

**绝对不能把全局变量定义在 .h 文件中：**

```c
// header.h
int g_val = 100;   // ❌ 如果被多个.c包含，会重复定义

// 正确的是：
extern int g_val;  // ✅ 在.h中只声明
```

同理，**头文件里的 `static` 变量会为每个包含它的 .c 文件生成一份独立副本**——看起来能用，实际上各文件操作的不是同一个变量，这是隐蔽的 bug 来源。

### 6.7 补充：const 的链接属性陷阱

前面 3.9 节提到过：**C 中文件作用域的 `const` 变量默认外链接，C++ 中默认内链接**。因此：

```c
// common.h —— 千万别这么干
const int kMax = 100;   // C 下外链接：多个.c包含 → 重复定义！
```

正确的做法是头文件里只声明、在某个 .c 里定义，或用宏/枚举替代：

```c
// common.h
extern const int kMax;  // ✅ 声明

// common.c
const int kMax = 100;   // ✅ 定义（外链接）
```

## 七、综合总结表

所有变量类型的完整对比：

| 变量类型 | 存储位置 | 作用域 | 生命周期 | 链接属性 | 默认初值 |
|---------|---------|--------|---------|---------|---------|
| 普通局部变量（auto） | 栈 | 代码块 | 临时 | 无链接 | 随机 |
| register局部变量 | 寄存器（可能） | 代码块 | 临时 | 无链接 | 随机 |
| 静态局部变量（static） | 数据段/bss段 | 代码块 | 永久 | 无链接 | 0 |
| 普通全局变量 | 数据段/bss段 | 文件作用域 | 永久 | 外链接 | 0 |
| 静态全局变量（static） | 数据段/bss段 | 文件作用域 | 永久 | 内链接 | 0 |
| 普通函数 | 代码段 | 文件作用域 | 永久 | 外链接 | - |
| 静态函数（static） | 代码段 | 文件作用域 | 永久 | 内链接 | - |
| 线程局部变量（C11） | 线程局部存储 | 视声明而定 | 线程期间 | 视关键字而定 | 0 |

## 八、工程实践建议

1. **尽量少用全局变量**：破坏模块化，增加耦合度。能用传参就用传参；
2. **全局变量必须在 .c 中定义，在 .h 中声明**：

```c
// module.h
extern int g_xxx;
// module.c
int g_xxx = 0;
```

3. **不跨文件访问的全局变量/函数一律加 static**：

```c
static int internal_counter;
static void internal_helper() {}
```

4. **volatile 一定要加对**：ISR 中、多线程共享、硬件寄存器地址——这 3 种情况必须加；
5. **不要返回局部变量的地址**（栈变量生命周期结束后无效）；
6. **register 不要随意使用**：编译器优化已经很好，乱用反而可能降低效率（占寄存器影响其他优化）；
7. **理解 C89/C99 的变量定义差异**：嵌入式环境很多仍用 C89/C90 标准，变量必须在函数开头定义。

## 九、嵌入式实战：从裸机到 RTOS

前面八节是纯 C 语言理论，这一节把它们放到嵌入式场景中验证——你会发现这些概念**直接影响程序能不能跑起来**。

### 9.1 裸机启动流程：谁在初始化 .data 和 .bss？

在操作系统下，程序加载器负责把 .data 段从可执行文件中加载到内存、把 .bss 段清零。但在裸机（无 OS）环境下，**没有任何人替你做这件事**，必须在启动文件里手动完成。

以 ARM Cortex-M（GNU 工具链）为例，`Reset_Handler` 的典型流程是：

```asm
Reset_Handler:
    ldr   sp, =_estack          ; 1. 设置栈指针（栈顶在 RAM 最高地址）
    ; 2. 拷贝 .data：把初始值从 FLASH 搬到 RAM
    ldr   r0, =_sdata            ; RAM 中 .data 起始地址
    ldr   r1, =_edata            ; RAM 中 .data 结束地址
    ldr   r2, =_sidata           ; FLASH 中 .data 初始值存放地址
copy_loop:
    cmp   r0, r1
    beq   zero_bss
    ldr   r3, [r2], #4
    str   r3, [r0], #4
    b     copy_loop
zero_bss:
    ; 3. 清零 .bss
    ldr   r0, =_sbss
    ldr   r1, =_ebss
zero_loop:
    cmp   r0, r1
    beq   call_main
    movs  r3, #0
    str   r3, [r0], #4
    b     zero_loop
call_main:
    bl    SystemInit              ; 4. 初始化时钟等
    bl    main                    ; 5. 跳转 main
```

其中 `_sdata`、`_edata`、`_sidata`、`_sbss`、`_ebss`、`_estack` 这些符号由**链接脚本（.ld 文件）** 定义，它们正是第五节讲的"静态存储期变量"在内存中的真实落点。

**如果启动文件里漏了 bss 清零会怎样？** 所有未初始化的全局变量初值都是随机值——这就是"裸机下全局变量初值不对"的根源。

### 9.2 用 map 文件验证变量落在哪个段

编译器/链接器生成 `.map` 文件，记录了每个符号的地址。查看 `Memory map` 和符号表部分：

```
Memory Configuration
...
*(.data)         0x20000000    0x100  main.o
*(.bss)          0x20000100    0x200  main.o

Symbol table
0x20000014   g_flag           .data   main.o
0x20000104   g_counter        .bss    main.o
0x20000124   s_task_stack     .bss    main.o
```

- `g_flag = 100` 显式初始化非 0 → 落在 `.data`（RAM 低地址，紧跟 FLASH 拷贝来的数据）；
- `g_counter` 未初始化 → 落在 `.bss`（零初始化）；
- `static int s_task_stack[...]` 未初始化 → 也在 `.bss`。

这个工具是嵌入式工程师核对"哪个变量占了多少 RAM、在哪个段"的必备手段。

### 9.3 volatile 与硬件寄存器映射

寄存器映射的经典写法（以 STM32 GPIO 为例）：

```c
#define GPIOA_CRL  (*(volatile uint32_t *)0x40010800)
```

- **必须 `volatile`**：寄存器值会被硬件随时改变，编译器不知道，不能缓存或合并读写；
- **必须是 `uint32_t *`**：保证按 32 位访问，且地址对齐；
- **必须强制类型转换**：把整型地址变成指针才能解引用。

如果不加 volatile，写 `while (UART_SR & TXE_BIT);` 这样的发送等待循环时，编译器可能把寄存器读优化成"读一次、用寄存器缓存"，导致死循环或漏判状态。

### 9.4 RTOS：任务栈与 static 任务控制块

以 FreeRTOS / uC/OS 为例，任务栈数组和任务控制块通常定义为 static：

```c
static StackType_t task1_stack[128];   // 任务栈：static → 放 .bss，RAM 中固定分配
static TaskHandle_t task1_handle;      // 任务句柄

void task1_entry(void *arg) {
    while (1) { ... }
}

int main(void) {
    xTaskCreate(task1_entry, "task1", 128,
                NULL, 1, &task1_handle);
    vTaskStartScheduler();             // 启动调度器
}
```

- 任务栈是**静态存储期**（.bss 段），不会因函数返回而消亡——任务函数体是一个死循环，栈必须常驻；
- 任务的"局部变量"其实分配在**任务自己的栈**上，而非系统栈（系统栈只有启动阶段和中断在用）；
- 任务控制块（TCB）和任务栈都靠 `static` 获得"永久生命周期 + 文件内可见"，这正是 3.3 节知识的直接应用。

### 9.5 嵌入式工具链的 C 标准差异速查

| 工具链 | 默认 C 标准 | 变量定义位置 |
|--------|------------|-------------|
| Keil MDK（armcc） | C90（C89） | 必须块开头 |
| IAR EWARM | C90 | 必须块开头 |
| arm-none-eabi-gcc | gnu11 / gnu17 | 任意位置（先定义后使用） |

老工程里"变量定义必须放在最前面"的代码风格，正源于 C89 标准——看到这种代码不要奇怪，兼容即可。

## 十、总结

最后用一张图回顾本文的核心脉络：

```
          定义位置 ──→ 作用域（谁看得见）
              │
存储类关键字 ──┤
（auto/register/static/extern）──→ 存储位置 ──→ 生命周期（活多久）
              │
              └──→ 链接属性（谁能用）
```

四个概念环环相扣：**存储类**决定变量**存在哪里**，进而决定它的**生命周期**；**定义位置**决定**作用域**；**关键字**决定**链接属性**。把它们放在一起理解，C 变量的"四维身份"就彻底清晰了。
